cdp-toolkit v1.9.4 · architectural atlas

An MCP server and CLI that drives named browser tabs over the raw Chrome DevTools Protocol and WebDriver BiDi — 45 tools, 35,034 lines across 90 indexed files, one runtime dependency. Every number on this page comes from a query against the codebase-memory graph (1,876 nodes / 5,326 edges) or from a grep of the source; nothing is estimated.

01 Executive summary

cdp-toolkit is a single-purpose browser driver for AI agents. Its whole design is one bet, stated as ADR-001 in src/driver.ts: put one browser-neutral Driver interface behind 45 tools, implement it twice — once over Chrome's DevTools Protocol, once over Firefox's WebDriver BiDi — and make every capability difference declared rather than discovered at runtime, so a tool a backend cannot run is simply absent from tools/list instead of present and throwing.

The five sentences

  1. It is a two-backend driver, not a browser wrapper. 35,034 lines, 41 source files, one runtime dependency — and the two largest files in the repo, src/cdp/driver.ts (1,854 lines) and src/bidi/driver.ts (1,436 lines), are structural twins implementing the same interface for two different protocols.
  2. The load-bearing centre is tiny and obvious. Every one of the 24 backend-neutral tools runs inside withPage() — an 8-line acquire/act/always-release envelope with 20 inbound callers — and every Chrome command goes through one CdpConnection.send (54 inbound edges, the graph's top hub).
  3. The public surface is a manifest, not a call graph. 45 tool names are declared in src/manifest.ts and dispatched through a 45-entry TOOLS registry in src/index.ts; the two sets reconcile exactly, but because dispatch is by table lookup the call graph sees none of them as called — which is why 33 src functions look dead and only 2 actually are.
  4. The real risk is twin drift, and the repo already knows it. src/bidi/driver.ts and src/cdp/driver.ts co-change 14 times with no import edge between them — the strongest hidden coupling in the repo — and src/manifest.ts, which nothing it describes imports, co-changes with shared-tools.ts, driver.ts and both drivers.
  5. It is well-tested where it is dangerous and thin where it is expensive. A 0.44 test-function ratio (168 test functions over 382 source ones) is healthy, but the coverage lives in unit tests for pure logic (leases, PNG stitching, selectors) while the two drivers are exercised mainly by hand-run smoke scripts that CI does not gate.

Top three findings

1. Two drivers, one interface, no compiler-enforced link between them. cdp/driver.ts and bidi/driver.ts both implement PageDriver, so TypeScript catches a missing method — but not a behavioural divergence. The graph shows the cost directly: 14 co-changes with zero imports between them, one structurally identical pair across the two files (driverError, Jaccard 1.00 — the same error constructor written twice), and 9 more method pairs the semantic index matches across them at 0.75–0.90, each one a same-named method implemented twice (resolveDragDestination, screenshot, intercept, resolveScrollPoint, hover, setFiles, drag, waitForEvent, and the uid codec pair decodeUid ↔ decodeStamp).
2. The dead-code signal is almost entirely an artefact of table dispatch. 33 src/ functions have no inbound CALLS edge, but 31 of them are reachable — as registry values, as manifest entries, or through references the extractor missed. Only 2 survive a grep of the whole tree: src/bidi/client.ts:335 connectBidiSession and src/driver.ts:109 uidHasScheme — and one of those documents itself as deliberately-kept back-compat.
3. The manifest is the real API and nothing enforces it at compile time. All 45 advertised schemas live in src/manifest.ts, a file that the code it describes never imports. The repo compensates with runtime and test guards (auditCoverage() in src/mcp.ts, test/manifest-grammar-drift.test.ts) — which is the right mitigation, and also the reason manifest.ts shows up in 6 of the top 20 co-change pairs.

02 System context

There are no services here and no HTTP surface of its own. cdp-toolkit is a local process that speaks two protocols outward — CDP over a WebSocket to Chrome, WebDriver BiDi over a WebSocket to Firefox — and one protocol inward: MCP over stdio, or argv from a shell.

Two binaries, one registry

BinaryEntryLifetime
cdp-toolkitdist/mcp.jsMCP stdio server (long-lived)
cdpdist/cli.jsone-shot CLI (one process per call)

Both dispatch through the same 45-entry TOOLS table in src/index.ts. The split matters for state: mcp.ts is long-lived (so strict lease mode is safe there and inert under the CLI), while cli.ts is one process per call — which is exactly why element references had to become process-independent strings (see ADR-001).

Import cycles

The src/ import graph is not a DAG: 9 distinct cycles exist, and every one of them runs through src/index.ts. The mechanism is a single edge — driver.ts imports the ToolName type from index.ts so that REQUIRED_CAPABILITIES is keyed by real tool names and the compiler catches a renamed tool, while index.ts imports every tool implementation, each of which imports driver.ts. It is a type-only cycle and harmless under verbatimModuleSyntax, but it is the reason no honest layered diagram of this repo exists.

05 API surface & entry points

This repo has no HTTP routes. Its API is 45 MCP tools, declared twice and reconciled: src/manifest.ts holds the JSON Schemas served by tools/list, and src/index.ts holds the TOOLS registry that dispatch actually indexes. Both sets were extracted and compared — they match exactly, 45 for 45. Availability is then filtered per backend by REQUIRED_CAPABILITIES ∩ the driver's own capability set.

The graph disagrees, and the graph is wrong. The index contains 5 Route nodes and 1 Channel node. All six are extraction artefacts: /etc/passwd and /tmp/a/b/c.txt are string literals in a path-safety test, /json/list is the CDP discovery URL this toolkit calls, /spool/frames.ffconcat is an ffmpeg argument, https://registry.npmjs.org comes from publish.yml, and the "socketio" channel is a generic error event listener in src/bidi/launch.ts. 06 Key flows

Three traces, taken with trace_path(direction="both") against the graph and read back against the source. Drawn as ordered steps rather than a rendered diagram library — same information, no CDN, nothing to fail.

A. Any tool call, end to end

The envelope every one of the 24 neutral tools runs inside.

1
MCP tools/call arrives
src/mcp.ts resolves the backend once at startup, checks the tool name against the capability-filtered set, and indexes TOOLS.
2
Registry lookup
src/index.ts maps the name to a function — onCdp(SHARED_TOOLS.x), a LEASE_TOOLS entry, or a per-module implementation.
3
withPage(driver, target, fn)
src/shared-tools.ts:72, 8 lines, 20 inbound callers. driver.page(target) → try { fn(page) } finally { page.release() }. This is the entire concurrency and cleanup story.
4
Target resolution + lease gate
driver.page() resolves the selector (active / index:N / url: / title: / label:) and calls assertLeaseOk — the choke point where strict mode auto-acquires a lease.
5
One socket, one command, one timeout
Chrome: CdpConnection.send over a fresh WebSocket with lazy per-domain enable. Firefox: BidiConnection.send on a refcounted module-scope session.
6
Always release
page.release() closes the CDP socket ("per-call" lifetime) or decrements the BiDi refcount ("session" lifetime). Tools never learn which they got.

B. take_screenshot past Chrome's 16,384px ceiling

The most-instrumented path in the repo, and the reason src/png.ts exists.

1
Resolve the ask
resolveScreenshotScale, resolveRenderSize, resolveTileMode — each a pure function, each independently unit-tested in test/screenshot-scale.test.ts (20 test functions, the largest test file).
2
Measure before capturing
One Page.getLayoutMetrics round trip. Chrome does not refuse an oversized capture politely — past 16,384 device px it can simply never answer — so the size is checked before the capture, not after.
3
Fits → one shot
writeOneShot, then imagePixelSize reads the real width/height back out of the encoded bytes rather than trusting the request.
4
Does not fit → bands
The driver captures vertical bands; stitch (shared-tools.ts:1314) hands them to stitchPngBandsToFile → stitchInto (png.ts:716), a hand-written PNG encoder/decoder with the deepest transitive loop nesting in the repo (transitive_loop_depth 9).
5
Restore what was emulated
renderRestoreFailureNote + the viewport record in the lease directory; the result reports renderRestored:false rather than silently leaving the tab emulated.

C. Lease acquisition under CDP_REQUIRE_LEASE

How several agents share one browser without stealing tabs.

1
Every target resolution funnels here
assertLeaseOk has three direct callers — shared-tools.resolvePage, client.resolveTarget, bidi.driver.resolveContext — and 12 more at two hops. There is no second door.
2
Read the lease file
readLease → leaseFile (11 inbound edges) under CDP_ARTIFACT_DIR. State is a file, deliberately: it must survive the CLI's one-process-per-call model.
3
Decide staleness
staleReason splits reclaimable (TTL elapsed — cheap, reversible) from reapable (TTL + CDP_REAP_GRACE_MS, destructive) and from dead pid (isPidAlive — reaped immediately, that process is not coming back).
4
Acquire or refuse
Strict mode auto-claims via claimLease/mintToken and marks the lease auto; an explicitly-claimed lease still demands its own token. Otherwise LeaseConflictError.
5
Touch on success
touchLease pushes lastUsedAt forward, so an agent working steadily never expires.

10 Decision timeline

There is no docs/adr/ directory and the graph carries no ADR store. The decisions live in two places: one numbered ADR written as a file header, and one dated design doc.

ADR-001 One browser-neutral Driver interface behind the 45 tools

Uid becomes an opaque tagged string (<scheme>:<payload>); CDP keeps cdp:<backendDOMNodeId>, BiDi STAMPS the page with data-cdp-uid instead of encoding a document-scoped sharedId; connection lifetime is declared ("per-call" for CDP, "session" for BiDi); anything one browser lacks stays out of the interface and is named in Capability, so tools/list omits it rather than throwing at runtime.

status: Adopted · in force · defined in src/driver.ts:1-57 · cited 30 times across 20 files
DESIGN 2026-08-08 Lease-required mode and close-on-release

One env switch (CDP_REQUIRE_LEASE, MCP-only) gates auto-acquire inside assertLeaseOk, new_page auto-claim, and reap-on-list; release_page closes tabs the origin ledger says the toolkit opened. CDP_REQUIRE_LEASE appears 96 times in src/ and is documented in the README, so the doc’s status line is stale.

status: Doc says "approved, not yet implemented", target 1.5.0 — actually SHIPPED in 1.9.x · defined in docs/design/2026-08-08-lease-required-and-close-on-release.md
Documentation drift, found by reading both. docs/design/2026-08-08-lease-required-and-close-on-release.md still reads "Status: approved, not yet implemented · Target release: 1.5.0". But CDP_REQUIRE_LEASE appears 96 times in src/, ships in the README config table, and the CHANGELOG first describes it under 1.7.0 — and there is no 1.5.0 release at all (the CHANGELOG jumps 1.4.0 → 1.6.0). The work landed; the design doc's status line did not follow it. That is a one-line fix and exactly the kind of thing a reader coming in cold would be misled by.

Release cadence

13 releases are recorded in CHANGELOG.md, from 1.0.0 (2026-06-24) to 1.9.4 (2026-08-11) — with nine of them in the eleven days from 2026-08-05 to 2026-08-11. This is a repo in a burst of active development, which is the correct context for reading the coupling numbers above: co-change counts are high because everything changed recently.
