# v2.1 — MCP-native lazy tool discovery

Status: **implemented** in 2.1.0 (2026-09-01); the findings below were measured against the real stdio entry point. Written 2026-09-01 against `cbd5870` (v2.0.0); §1–§7 are preserved verbatim as the original brief — the record of what was asked — and §0 is the answer.

2.0.0 shipped progressive disclosure as a home-grown mechanism: a `core` tool profile plus
a `browser_tools` meta-tool that activates further groups on demand. This document is the
brief for 2.1 — establish whether the MCP spec and ecosystem have since converged on a
**standard** way to do lazy tool discovery, and re-base the mechanism on it if so.

Everything below marked **MEASURED** was probed against a real stdio server. Everything
marked **UNVERIFIED** is a thread to pull, not a finding. Do not promote the second kind
into the first without a probe.

---

## 0. Outcome — MEASURED

Shipped as **2.1.0**. Every number and every protocol claim about *this server* below was
probed over raw stdio JSON-RPC against `bun src/mcp.ts`, the same entry point every
registration uses, and every negative result is paired with a positive control (e.g.
`browser_tools` → `unknown tool: browser_tools` alongside `describe_tool` answering
normally on the same connection). Where a claim is about a *host* rather than about this
server, its evidence class is named inline.

### The loose thread, resolved

`"2026-07-28"` is **`SUPPORTED_MODERN_PROTOCOL_VERSIONS`** in
`@modelcontextprotocol/server/stdio` — a separate constant from `SUPPORTED_PROTOCOL_VERSIONS`,
which is why §2's grep found the literal in the packages but not in the version list. It is the
current revision, and it is reachable **only** through `serveStdio` (or the HTTP
`createMcpHandler`), never through `Server.connect(transport)`.

### Was 2.0.0 really on the current protocol? — **No**

Probed raw over stdio, v2.0.0 answered `server/discover` with **`-32601 Method not found`** and
served a `tools/list` carrying no `resultType`, no `ttlMs`, no `cacheScope`. It was a
**2025-11-25 (legacy-era) server running on the 2.0 SDK**: the package number had moved, the
protocol era had not, because `Server.connect(new StdioServerTransport())` *is* the legacy path.
§3's real question — "does the code use SDK 2.0 idioms, or the 1.x low-level shape 2.0 merely
kept working?" — had the second answer, and on the axis that mattered it was not a style
question at all.

### §3, the SDK-idiom questions

- **Is there a higher-level registration API that is now the supported path?** Yes,
  `McpServer.registerTool`, and it was **rejected on two grounds**. It requires a
  Standard-Schema object (zod) for `inputSchema`, and `CONTRACT.md` rule 1 forbids any runtime
  dependency beyond the SDK — the manifest is plain JSON Schema (`src/manifest.ts`). It also
  cannot express "unlisted tools remain callable by name", which is the entire point of
  `CDP_TOOL_PROFILE`.
- **Is string-literal `setRequestHandler` deprecated?** Deprecated *in favour of* `McpServer`,
  and still supported for "advanced use cases". It is the v2 form `McpServer` itself is built
  on, and `McpServerFactory` explicitly accepts a `Server`. Keeping the low-level `Server` is a
  supported choice, not 1.x residue. **The real gap was the transport, not the handler API.**
- **Does any capability introduced at `2025-06-18` or `2025-11-25` bear on tool discovery?**
  No. Nothing in either revision touches lazy discovery.

### §4, the four research questions

1. **Does the spec define a first-class mechanism for tool filtering / lazy discovery?** Yes —
   at **2026-07-28**, and it settles the question on the **host** side. The host runs a
   catalog → inspect → execute funnel (its own search/details meta-tools over the servers'
   lists). A *server* cooperates by publishing a **complete, deterministic, cacheable**
   `tools/list`: `ttlMs` and `cacheScope` are REQUIRED on modern results, `server/discover`
   replaces `initialize`, requests carry a `_meta` envelope, and the tool set **MUST NOT change
   as a side effect of other requests on the connection**. See
   <https://modelcontextprotocol.io/docs/2026-07-28/develop/build-server> and
   <https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices>.
2. **How do first-party servers do it — is this an alignment job?** Yes, and the alignment is
   narrower than §4 guessed: GitHub-toolsets-style server-side filtering is a **startup
   configuration knob**, not a runtime protocol feature. That is exactly what
   `CDP_TOOL_PROFILE` now is — read once, fixed for the process's life.
3. **Is there a client-side convention to cooperate with rather than duplicate?** Yes: the
   host's funnel above. `browser_tools` was duplicating it *and* violating it. The
   client-best-practices page also warns that adding or removing tool definitions
   mid-conversation invalidates the host's prompt cache. §4's asymmetry — deferring clients pay
   little for a complete list, eagerly-loading ones pay the full 88% — was real, and its
   conclusion ("it argues against one global default") is honoured by making the profile a
   deployment knob and defaulting to the standards-conformant option.
4. **Does pagination actually reduce what a client loads?** **No.** `tools/list` cursor
   pagination is a transport convenience; hosts page through the whole list. Not adopted.

### The constraint most likely to bite — **moot**

§4's open thread was "does a given client re-fetch `tools/list` on `notifications/tools/list_changed`?"
2.1 does not answer it — it **removes the need to ask**. The listing is computed once, frozen,
and returned byte-identical on every call and every connection; `capabilities.tools.listChanged`
is `false`; `browser_tools` is gone. A trap that depended on a mid-session notification landing
cannot fire when no notification is ever sent.

### The design decision

- **Discovery is the host's job.** The server's contribution is a complete, deterministic,
  cacheable list, not a mechanism of its own.
- **The listing is static.** `describe_tool` first, then manifest order, filtered by backend
  availability and then by the profile; computed once at startup and frozen.
- **Cache hints:** `ttlMs: 3_600_000`, `cacheScope: "public"` on both `tools/list` and
  `server/discover` — public because a stdio server has no per-caller auth, so the list is
  identical for everyone. A restart under a different `CDP_TOOL_PROFILE` or `--browser` is a
  different server configuration, not a mid-life change to this one.
- **Dual-era transport:** `serveStdio` with the default `legacy: 'serve'`. Modern opening →
  `server/discover`, `supportedVersions: ["2026-07-28"]`, `resultType: "complete"`,
  `_meta['io.modelcontextprotocol/serverInfo']`. 2025-era opening → `initialize` →
  `protocolVersion "2025-11-25"`, unchanged.
- **Default profile flipped `core` → `full`**, for the three reasons in §6 and above:
  host-side discovery makes a complete list cheap on a deferring client; consumers holding
  per-tool allowlists or per-tool interception keyed on tool NAME for non-core tools (console
  and network readers, `performance_analyze_insight`) were silently broken by a `core` default,
  since those tools were absent from `tools/list`; and a list that never changes never
  invalidates the prompt cache.
- **`browser_tools` removed.** `describe_tool` absorbed its useful half: `name` is now optional,
  and with no name it returns the grouped catalog (1,141 characters for the whole 45-tool
  surface) that `list_groups` used to report.
- **`CDP_TOOL_PROFILE` also accepts a comma-separated group list** (`core,network,console`),
  with `core` always included; an unknown group name exits 1 with
  `CDP_TOOL_PROFILE: unknown tool group 'x'. Known: full, core, input, …`.
- **Unlisted stays callable.** Measured: under `core`, `list_leases` executes.

### Host protocol eras — capability vs behaviour

Two different classes of evidence, kept apart on purpose.

- **Capability, from binary string presence:** the Claude Code and Codex binaries carry the
  modern-era client strings (`server/discover`, the `_meta` protocolVersion key); the opencode
  binary does not. This is evidence that the capability is *present*, and evidence of nothing
  about what any of them does by default.
- **Behaviour, MEASURED 2026-09-01:** two real hosts were pointed at the 2.1 server through a
  wrapper that tees the server's stderr to a log, and the per-connection era line was read back.
  **Claude Code 2.1.258** (`claude -p --mcp-config … --strict-mcp-config`) and **Codex CLI
  0.147.0** (`codex exec -c mcp_servers…`) both connected, and **both logged
  `connection pinned to the legacy protocol era`** — today both still open with `initialize`
  (2025-11-25) despite carrying the modern client strings. The SDK 2.0.0 `Client` does the same
  by default; an SDK-client consumer pins the legacy era unless it opts in via
  `versionNegotiation`.

Three consequences, stated plainly:

1. The dual-era default (`legacy: 'serve'`) is **load-bearing, not courtesy**. A modern-only
   server would be unreachable from every host measured on this machine today.
2. The modern era is currently exercised only by the raw-stdio test suite and by the SDK client
   pinned to `2026-07-28` in `mcp:smoke`. **No host is claimed to use it yet.**
3. The static, cacheable listing still pays off on a legacy host — no mid-session tool churn, no
   prompt-cache invalidation — but the `ttlMs`/`cacheScope` hints are emitted only on modern
   connections.

## 4. The research task

### What exists today

- `src/toolGroups.ts:1-49` — 13 groups (`core`, `input`, `cookies`, `network`, `console`,
  `mocking`, `emulation`, `performance`, `recording`, `leases`, `permissions`, `dialogs`,
  `downloads`), `GROUP_TOOLS`, `TOOL_GROUP` reverse map, `PROFILES = {core, full}`
- `src/mcp.ts:76` — `START_PROFILE` from `CDP_TOOL_PROFILE` (`full`, or default `core`)
- `src/mcp.ts:80-120` — `META_TOOLS`: `browser_tools`
  (`list_groups|activate|deactivate|set_profile`) and `describe_tool`
- `src/mcp.ts:132` — declares `capabilities.tools.listChanged: true`
- `src/mcp.ts:134-144` — `tools/list` = meta-tools + manifest entries whose group is
  active **and** whose backend supports them
- `src/mcp.ts:150-190` — `tools/call` intercepts both meta-tools before browser dispatch;
  a group change calls `server.sendToolListChanged()` (`src/mcp.ts:181`)
- `src/toolDocs.ts` — the full pre-2.0 prose, served on demand by `describe_tool`; the
  live manifest carries only terse one-liners

### Questions to answer from sources, not memory

- Does the spec at `2025-11-25` (or later) define a **first-class** mechanism for tool
  filtering or lazy discovery? Look specifically at `tools/list` **cursor pagination**,
  tool namespacing, `_meta`, tool annotations, and any dynamic-tools or tool-search SEP.
- How do reference and first-party servers do it — GitHub's MCP server "toolsets",
  `chrome-devtools-mcp`, `playwright-mcp`, the SDK's own examples? GitHub's toolsets look
  closest to what is already here; if so, **2.1 is an alignment job on naming and
  semantics, not a rewrite.**
- Is there a client-side convention a server should cooperate with rather than duplicate?
  Some clients already defer MCP tool schemas — the session listing carries tool *names*
  only, and schemas load on demand. On such a client the full 47-tool manifest costs
  little context and `core` mostly buys a round trip, while a client that eagerly loads
  the whole manifest gains the full 88%. **That asymmetry is the real input to the 2.1
  default, and it argues against one global default.**
- If the standard turns out to be pagination, does paginating a full list actually reduce
  what a client loads, or does only the meta-tool approach do that? Answer before
  adopting it.

### The constraint most likely to bite

`listChanged` is declared and `sendToolListChanged()` fires. **UNVERIFIED: whether a given
client re-fetches `tools/list` on that notification mid-session.** If a client does not,
`core` is a trap there — the 33 hidden tools stay unreachable until restart — and 2.1
needs a different default for it, or a documented per-client recommendation. Verify with a
live session per client. A negative result from a probe you wrote is a claim about the
probe until a positive control says otherwise, so pair it with a case that must succeed.

## 6. Compatibility constraints

Downstream consumers vendor this server and register it per harness, so the 2.1 default
profile has to be defensible on a client that eagerly loads the manifest *and* on one that
defers schemas.

Two concrete ones to design around:

- **Some consumers maintain per-tool permission allowlists** naming tools outside the
  `core` profile — the console and network readers and `performance_analyze_insight` are
  the common ones. Under `core` those entries reference tools the client cannot see.
- **Some consumers attach per-tool interception keyed on the tool NAME.** A tool absent
  from `tools/list` is not callable, so its interception never fires either. Tool names
  were unchanged in 2.0.0; **keep them unchanged in 2.1.**

## 7. Do not

- Change tool names, parameters, or schema shapes. 2.0.0 gated itself on a
  strip-descriptions deep-equal against the prior manifest, and downstream consumers match
  by name.
- Add a runtime dependency — `CONTRACT.md` rule 1. The MCP SDK is the only one, and
  `lighthouse` is a subprocess exception.
- Assert the mechanism works because the docs say so. Probe the real stdio entry point,
  and pair every check with a control that must come out different.
